# 10. Перенос данных, инфраструктура и выкат

## 1. Что есть сейчас (факты, проверено)

| Компонент | Текущее состояние |
|---|---|
| Сайт | Статические HTML/CSS/ассеты в `/var/www/lideryprava`, nginx отдаёт напрямую |
| API | `server.py` (546 строк, только stdlib) под `systemd lideryprava.service`, nginx проксирует `/api/` на `127.0.0.1:8090` |
| БД | SQLite `data/applications.db` (WAL), одна таблица `applications` — плоская анкета физлица (ФИО, e-mail, телефон, организация, статус, заметки, согласия, IP) |
| Админка | `admin.html`, вход по cookie `leaders_admin_session`, функции: список, поиск, фильтр, статусы, заметки; ролей нет; выгрузки нет |
| Файлы | Загрузки материалов **нет** |
| TLS | Let's Encrypt (certbot --nginx), HSTS 1 год, HTTP/2 |
| Бэкапы | systemd-таймер 03:30 → `/root/db-backups/lideryprava/*.db.gz` (30 копий) + off-site pull на Mac |
| SEO | `sitemap.xml` (6 URL), `robots.txt` = `Allow: /`, два файла верификации Mail.ru по фиксированным путям, canonical и JSON-LD на главной и «Победителях» |
| Аналитика | Отсутствует |
| Дрейф | Репозиторий ≠ прод: боевой `server.py` содержит `/api/health`, порт в юните отличается от nginx (8000 против 8090), пароль в юните-образце `change-me-please` |
| Soft-404 | Любой несуществующий путь отдаёт `200` и главную страницу |

| Артефакт | Почему |

| Данные SQLite `applications` | Заявки сезона 2026 и подтверждения согласий |
| Канонические URL главной и «Победителей» | SEO |
| Бэкапы БД на сервере и off-site | Восстановление |

## 3. Этапы переноса

### Этап 0. Подготовка (до любых изменений)

1. **Закрыть публичный доступ к служебным файлам** (критично, см. 11): сейчас по HTTP доступны `/data/applications.db`, `/data/applications.db-wal`, `/data/auth.log`, `/server.py`, `/scripts/backup_db.py`, `/scripts/purge_expired.py`.
2. Снять слепок прода: актуальный `server.py`, боевой `lideryprava.service` с переменными окружения, `nginx_lideryprava.conf`, список файлов в каталоге сайта.
3. Сделать дамп SQLite (`sqlite3 .backup`, а не копирование файла), проверить его открытие и число записей.
4. Зафиксировать перечень URL, отдающих `200`, и текущие коды ответов для сравнения после выката.
5. Убедиться, что репозиторий на `main` соответствует проду, и зафиксировать расхождения.

### Этап 1. Новая платформа в репозитории

1. Ветка `feature/lidery-prava-platform`: платформа в `platform/`, текущий сайт переносится в `legacy-site/` (файлы не удаляются).
2. Миграции БД `liders` применяются на пустой БД без ошибок.
3. Гейты разделения (раздел 03, п. 6) проходят.

### Этап 2. Тестовый стенд

1. Отдельная БД `liders_stage` и отдельный каталог файлов.
2. Наполнение: сезон 2027, критерии, партнёры, документы.
3. Приёмка по сценариям раздела 12, включая подачу заявки, вход в кабинет, загрузку материалов, оценку, публикацию протокола.
4. Проверка на реальных данных: полная подача тестовой заявки через мастер `/apply` и разбор её в админке.

### Этап 3. Перенос данных

1. **Заявки сезона 2026** из SQLite переносятся в таблицу `legacy_applications` (полная копия полей + `migrated_at`), доступную в админке только на чтение и экспорт. Это сохраняет историю и не смешивает старую плоскую модель с новой командной.
2. При наличии согласий — сохраняются отметки и время согласия без изменений.
3. Публичный контент (тексты, партнёры, победители, FAQ) переносится в БД через админку или сиды.
4. Юридические документы заменяются на новые (раздел 09); старые версии сохраняются как архивные.
5. Ассеты (логотипы партнёров, изображения) переносятся с сохранением имён или с редиректами.

### Этап 4. URL и SEO

1. Таблица редиректов `301` для всех изменившихся адресов; правило: старый URL всегда ведёт на наиболее близкую новую страницу, а не на главную.
2. Сохраняются точные пути: `/`, `/pobediteli.html` → `/winners` (или сохраняется оба), `/privacy.html` → `/legal/privacy`, `/soglasie.html` → `/legal/pdn-consent`, `/terms.html` → `/legal/terms`, `/cookies.html` → `/legal/cookies`, `/legal.css` (оставить или редирект).
3. Файлы верификации Mail.ru отдаются по прежним путям без изменений.
4. Обновляются `sitemap.xml` (все новые страницы, включая мастер-классы и документы) и `robots.txt` (закрыть `/cabinet/`, `/admin/`, `/api/`).
5. `canonical` и `description` появляются **на всех** индексируемых страницах (сейчас у юридических страниц их нет).
6. JSON-LD: `Organization` (Ассоциация), `Event` (конкурс), `FAQPage` (частые вопросы), `BreadcrumbList`.
7. **Честный 404** вместо текущего soft-404.
8. Подключение Яндекс.Метрики (и, при необходимости, иных счётчиков) — только после согласия на куки; номера счётчиков предоставляет Оргкомитет.

### Этап 5. Выкат

1. Порядок: остановка приёма заявок не требуется, но выкат выполняется **вне периода пиковой подачи** и не в последние 24 часа перед дедлайном.
2. Перед выкатом: полный дамп БД + слепок каталога сайта, отметка точки отката.
3. Развёртывание: новая БД `liders`, новые systemd-юниты (`liders-api`), nginx-конфиг со статикой новой сборки и проксированием `/api/`.
4. Проверка по чек-листу: 14 публичных маршрутов отдают `200`, API отвечает, вход в админку работает, кабинет открывается по токену, материалы загружаются, старые URL редиректят, `sitemap` доступен, верификационные файлы на месте.
5. Старый `server.py` останавливается, но **не удаляется** 30 дней (точка отката).
6. Мониторинг первые 72 часа: журналы ошибок, доступность, обработка заявок.

### Этап 6. После выката

1. Сверка числа заявок и материалов с ожидаемым.
2. Проверка почты: письма о заявках и доступах доходят (тест на внешние ящики Mail.ru, Яндекс, Gmail).
3. Проверка индексации: старые URL отдают `301`, новый `sitemap` принят.
4. Разбор обращений первых дней и правки формулировок.
5. Через 30 дней — удаление старого кода и `server.py` после подтверждения стабильности.

## 4. Инфраструктура целевого решения

| Компонент | Решение |
|---|---|
| Веб-сервер | nginx: статика новой сборки + проксирование `/api/` на локальный порт API |
| API | `systemd`-юнит `liders-api`, `Restart=always`, пользователь без прав root |
| БД | PostgreSQL на том же сервере (или управляемая БД в РФ), отдельная БД `liders` |
| Файлы | Каталог вне корня сайта, `media` в БД для материалов |
| Секреты | Файл окружения с правами `600`, владелец — служебный пользователь; в git не попадает |
| TLS | Сохраняется текущая схема certbot; автопродление проверяется |
| Бэкапы | Ежедневный `pg_dump` 03:30 + off-site pull, хранение 30 копий, шифрование |
| Журналы | Ротация (logrotate), срок хранения 90 дней; ПДн в журналы не пишутся |
| Мониторинг | Проверка `GET /api/health` каждые 5 минут, уведомление при недоступности |

## 5. Откат

1. Условия отката: критические ошибки приёма заявок, недоступность кабинета, потеря данных, ошибки авторизации более 30 минут.
2. Процедура: включить прежний nginx-конфиг и `lideryprava.service`, вернуть статику из слепка, восстановить SQLite при необходимости.
3. Данные, поданные через новую платформу до отката, сохраняются в БД и переносятся повторно после исправления — потеря заявок недопустима.
4. Ответственный за решение об откате назначается до выката; решение фиксируется письменно.

## 6. Что делать нельзя

1. Выкатывать новую платформу без дампа БД и слепка каталога.
2. Удалять `legacy-site/` и старый `server.py` до истечения 30 дней стабильной работы.
3. Менять `robots.txt` на `Disallow: /` в период индексации.
4. Переносить старые плоские заявки в новую командную модель «напрямую»: модели разные, нужна отдельная таблица истории.
5. Оставлять пароль администратора в юните или в репозитории.
