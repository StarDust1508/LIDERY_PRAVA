# 11. Безопасность и защита персональных данных

## 1. КРИТИЧНО: устранить до начала работ

### 1.1. Что обнаружено

На действующем сайте nginx отдаёт статику из того же каталога, где лежат код и база данных. В результате по HTTP без авторизации доступны:

| Путь | Что это | Подтверждение |
|---|---|---|
| `/data/applications.db` | База заявок SQLite с персональными данными | Ответ `200`, сигнатура SQLite |
| `/data/applications.db-wal` | Журнал незачекпойнченных транзакций (свежие данные) | Ответ `200`, 173 КБ |
| `/data/auth.log` | Журнал входов в админку (IP, время) | Ответ `200` |
| `/server.py` | Исходный код бэкенда | Ответ `200` |
| `/scripts/backup_db.py`, `/scripts/purge_expired.py` | Служебные скрипты | Ответ `200` |

Содержимое базы при проверке не выгружалось, но сам факт публичной доступности файла с ПДн — это инцидент по 152-ФЗ: персональные данные участников (ФИО, e-mail, телефон, организация, IP) находились в открытом доступе для любого лица, знающего адрес.

### 1.2. Немедленные действия (до всех остальных работ)

1. Запретить отдачу служебных путей на уровне nginx и проверить результат:

```nginx
# Внутри server { ... } для lideryprava.ru
location ~ ^/(data|scripts)/        { deny all; return 404; }
location ~* \.(py|db|db-wal|db-shm|log|sql|env|bak|gz|tar)$ { deny all; return 404; }
location ~ ^/(server\.py|deploy\.sh|setup_server\.sh|start_server\.sh|run_server\.sh)$ { deny all; return 404; }
```

2. Проверить, что пути больше не отдаются: `curl -I https://lideryprava.ru/data/applications.db` → `403`/`404`.
3. Перенести базу и служебные каталоги **за пределы корня сайта** (`/var/lib/lideryprava/`), чтобы конфигурация nginx не была единственной защитой.
4. Убедиться, что каталоги `data/`, `scripts/`, `private/` недоступны и не имеют листинга.
5. Проверить журналы nginx за прошлый период на предмет обращений к этим путям — если файлы скачивались посторонними, это основание для уведомления Роскомнадзора об инциденте; решение принимает Ассоциация как оператор ПДн.
6. Сменить пароль администратора и все служебные пароли после закрытия доступа (на случай, если `auth.log` и конфигурация были доступны).

### 1.3. Почему это блокирует перенос

Переносить данные из базы, которая была публично доступна, без оценки инцидента нельзя: неизвестно, были ли данные скачаны. До закрытия доступа и решения Оргкомитета работы по переносу данных не начинаются.

## 2. Управление секретами

1. Все секреты — только в файле окружения с правами `600` и владельцем-служебным пользователем; в git не попадают (`.gitignore` уже исключает `.env`).
2. При старте проверяются обязательные переменные: `DATABASE_*`, `JWT_SECRET`, `ADMIN_SESSION_SECRET`, `ADMIN_PASSWORD` (первичный), `DOWNLOAD_SECRET`. Отсутствие — остановка процесса с понятным сообщением.
3. `ADMIN_SESSION_SECRET` — не короче 32 символов; в продуктивном режиме короткий ключ приводит к отказу запуска (в доноре — к `503`, это подтверждённое поведение, сохраняем).
4. Пароли администраторов — `bcrypt`, cost ≥ 12. Пароль в открытом виде не хранится нигде, включая systemd-юнит (в текущем юните образца — `change-me-please`; в новой конфигурации пароль в юните отсутствует).
5. Ротация: сессионные ключи — раз в год и при смене ответственного; пароли админов — раз в полгода и при увольнении.
6. Секреты разных окружений (тест/прод) не совпадают.
7. Доступ к серверу — по SSH-ключам, вход по паролю отключён; root-доступ используется только для обслуживания.
8. Резервные копии, выгружаемые за пределы сервера, шифруются; ключ хранится отдельно от копий.

## 3. Разграничение доступа

| Контур | Доступ |
|---|---|
| Публичный | Только опубликованные материалы; никаких ПДн, никаких файлов команд |
| Кабинет команды | Только своя команда; проверка принадлежности на сервере для каждого запроса |
| Эксперт/Жюри | Только назначенные материалы и свои оценки |
| Оператор | Заявки, материалы, обращения, контент; без пользователей, настроек и публикации протоколов |
| Администратор | Всё |
| Сервер | Ключи SSH, служебный пользователь без лишних прав |

Правила: принцип наименьших прав; права проверяются на сервере; интерфейс скрывает недоступное, но это лишь удобство, а не защита.

## 4. Загрузка файлов

1. Белый список MIME-типов и расширений: PDF, DOC, DOCX, RTF, ODT, XLS, XLSX, PPT, PPTX, PNG, JPEG, ZIP.
2. Проверка **magic-байтов**, а не только заголовка `Content-Type` (приём из донора).
3. Лимит размера — из переменной окружения (по умолчанию 25 МБ на файл).
4. Имя файла не используется как путь: файлы хранятся под внутренними идентификаторами; исходное имя сохраняется как метаданные.
5. Исполняемые файлы (`.exe`, `.sh`, `.js`, `.php`, `.py`, `.html`) отклоняются.
6. Файлы отдаются с заголовком `Content-Disposition: attachment` и без исполнения; для PDF-просмотра — `inline` только для собственных документов сайта.
7. Архивы не распаковываются на сервере автоматически.

## 5. Безопасность приложения

1. **Заголовки:** `Content-Security-Policy` (без `unsafe-inline` для скриптов), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, HSTS.
2. **CORS:** строгий список источников (`https://lideryprava.ru`, `https://www.lideryprava.ru`); никаких `*` для эндпоинтов с данными.
3. **CSRF:** для изменяющих запросов из браузера — проверка `Origin` и токен; cookie сессий `SameSite=Lax` и `HttpOnly`.
4. **Rate-limit:** вход в админку 8/мин с IP, вход по токену 10/мин, публичные приёмные формы 10/мин, «получить ссылку заново» 3/час на команду.
5. **SQL:** только параметризованные запросы; конкатенация значений в SQL запрещена.
6. **XSS:** вывод пользовательских текстов экранируется; markdown-контент санитизируется; `dangerouslySetInnerHTML` без санитайзера запрещён.
7. **Файлы и ссылки:** внешние ссылки материалов проверяются по белому списку доменов (РФ), протоколы кроме `https:` отклоняются.
8. **Идентификаторы:** доступ к материалам и файлам проверяет права, а не «неугадываемость» URL.
9. **Ошибки:** пользователю — понятное сообщение и `requestId`, без стеков и деталей БД.
10. **Журналирование:** без ПДн; фиксируются идентификаторы, действие, результат.

## 6. Соответствие 152-ФЗ

1. Оператор ПДн — Ассоциация; сайт и БД физически в РФ.
2. Обрабатываются только данные, необходимые для конкурса: ФИО, дата рождения, контакты, организация, сведения об образовании/опыте, конкурсные материалы, изображение (при согласии).
3. Всякое расширение состава данных требует правки политики и, при необходимости, уведомления Роскомнадзора.
4. Согласия раздельные и доказуемые: фиксируются версия документа, время, IP (см. 09, п. 5).
5. Ретенция: 3 года с завершения сезона, затем удаление или обезличивание; ежегодная проверка и журналирование.
6. Права субъекта: доступ, исправление, удаление, отзыв согласия — реализуются через ответственного за ПДн с инструментами в админке.
7. Инциденты: порядок из п. 1.2 применяется и к будущим инцидентам; решение об уведомлении принимает оператор.

## 7. Резервное копирование и восстановление

1. Ежедневный дамп 03:30 (МСК), 30 копий, проверка целостности дампа сразу после создания.
2. Раз в месяц — тестовое восстановление в отдельную БД с проверкой числа записей.
3. Хранение за пределами сервера — в зашифрованном виде.
4. Доступ к копиям ограничен; копии не попадают в git и в публичные каталоги.
5. Процедура восстановления описана и проверена; ответственный назначен.

## 8. Процесс разработки

1. Секреты и реальные ПДн не попадают в репозиторий, тесты и скриншоты. Тестовые данные — вымышленные.
2. Перед каждым выпуском: `tsc --noEmit`, тесты, гейты разделения (раздел 03), проверка миграций на пустой БД.
3. Зависимости проверяются на уязвимости (`npm audit`); критические — устраняются до выпуска.
4. Ветка `main` защищена: изменения только через слияние проверенной ветки; прямые push в `main` запрещены.
5. Репозиторий приватный; публикация кода без явного решения владельца запрещена (сделано: репозиторий переведён в приватный).

## 9. Что считается недопустимым

1. Хранение БД или служебных файлов внутри корня сайта.
2. Секреты в репозитории, юните systemd или в переписке.
3. Общий пароль администратора на нескольких людей.
4. Отправка ПДн в мессенджеры и на личные адреса.
5. Публикация данных участников и материалов команд без согласия.
6. Отключение проверок безопасности «временно», без даты возврата.
